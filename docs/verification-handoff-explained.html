Why simplify?

Don't make the guide build a new machine.

The direction we want to avoid

“Before I can answer, I need another launcher, another sandbox policy, and a particular tool version.”

A custom execution layer adds more setup that can fail. The guide spends its time maintaining the machine instead of finishing your question.

The proposed direction

“I'll use the comparison tools we already have and carry the work through.”

If something breaks, fix it in the part that owns it. Don't create another system to work around it. Keep the question—and you—out of the setup maze.

Simpler does not mean ignoring permissions or disabling safety. If the existing tools cannot safely answer the question, explain the real limit rather than bypass it.

When something goes wrong

A broken camera isn't always a broken test.

Are we checking a decision?

If we ask, “Does the agent ask for approval before using a picture?”, an agreed pretend image service may be enough. We watch the agent's actual choices.

We do not automatically need real artwork generation.

Or are we checking the real service?

If we ask, “Can it generate, save, and inspect the picture?”, a pretend service cannot answer that. Missing image support is a real limit.

We must not quietly change the question.

First: one real visit

Try the whole journey.
Then improve the workshop.

Use one real instruction change, the actual handoff, behavior-rehearse, and the existing runner. Look for where you still have to help.

Do not wait for a perfect architecture before trying it.

  • You don't have to say “continue.”
  • You don't have to debug the setup.
  • The comparison actually runs and captures the needed evidence.
  • You understand what to keep, change, or investigate next.

These are proposed acceptance checks, not results already achieved. One successful visit does not prove every future visit will work.

The tradeoff

Less machinery. Still needs proof.

What gets simpler

One owner for your question. One place for comparison rules. One existing execution path. Fewer overlapping instructions and fewer new prerequisites.

What this does not solve by itself

The agent can still miss a step. A host tool can still fail. Shared context can still influence a comparison. Clear responsibilities help us find the right fix; they don't guarantee success.

What about isolation—and the more elaborate designs?

Keep the answer sheet away from the test takers. Trial inputs should not contain expected answers or previous outcomes. Fresh context and the host's safety controls still matter. A new custom sandbox is not automatically required, but a required boundary must not be silently dropped.

Proving the visit works is different from proving why a rule works. Completing this journey does not prove that every observed difference came only from the changed instruction. We must state the comparison's actual limits.

Later, if needed: clearer saved handoff records could help recover interrupted work. A small coordinator could help multiple callers. Neither is a prerequisite for the first walkthrough, and neither should duplicate the runner.

Our next decision: agree on the journey, make only the changes needed to try it, and review what really happened before refining the architecture.
