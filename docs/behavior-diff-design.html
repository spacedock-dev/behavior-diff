Proposed architecture · explained simply · not implemented yet

A little workshop.
One job at each table.

Imagine we are testing two sets of instructions for building a toy tower. Did the new instructions change what the builder did? And did they help?

Behavior Diff is that workshop for AI agents. Instead of one helper doing everything, each helper does one job and leaves a labeled result for the next helper.

01 / Walk through the workshop

Same test. Different instructions.

Read the tables in numbered order. These pictures explain responsibilities—not real trial results. A table is a stage: one job with clear inputs and outputs.

Six jobs. No extra evidence-checking table.

1
The host agent

Plan a fair test

Choose the task and the blocks. Give both versions the same starting materials. Decide what to check before seeing the results.

Leaves: a frozen plan. The private checklist stays away from the builders.

2
The runner + trial agents

Try both versions

Fresh builders follow the old and new instructions. The runner saves what they actually do and say, including unfinished attempts.

Leaves: original recordings. Finishing the task is not the same as doing it correctly.

3
Deterministic code

File the evidence

Put the recordings in order and give each piece an address. Keep the originals. Mark missing pieces instead of guessing what happened.

Leaves: an evidence index. This is sorting and bookkeeping, not judging.

4
A fresh observer

Say what happened

“This builder added a wider base.” Describe actions and answers without receiving our separate goal sheet or the instruction edit.

Leaves: cited observations. Not a “good” or “bad” score.

+
Example future stage

Check for missing proof

“We wanted to check stability, but nobody recorded a stability test.” This helper checks whether the needed evidence is available.

Needs: the frozen checklist + evidence index.
Leaves: a coverage note for the assessor—not for the observer.

5
A fresh assessor

Check the goal

Now open the goal sheet. Was the tower actually stable? A wider base alone does not prove it. Check permitted excerpts from the recordings, not just the observer’s notes. Private raw recordings stay local.

Leaves: an assessment. “Not enough evidence” is a valid answer.

6
The renderer + host explanation

Show one honest report

Print the observations, assessment, and links to proof. The host explains that saved result. You decide whether to keep the instruction change.

Leaves: a report. Printing it again does not repeat the experiment.

The pictures show jobs, not a fixed schedule. A job starts when its required inputs are ready. The extra evidence check has no dependency on observation; the assessor waits for both when that check is required. This permits concurrency without requiring it.

02 / How helpers cooperate

Pass a labeled folder.
Not your whole desk.

A helper should not need to know how the previous helper works. It only needs the agreed contents of the folder.

In software, the folder is a saved artifact: structured data or evidence files with a clear format.

Every folder says:

“Here is what I contain.”
“Here are the inputs I used.”
“Here is the version that made me.”
“Here is what is missing or went wrong.”

Keep earlier folders unchanged. A later helper adds a new result instead of rewriting the evidence.

03 / Growing the workshop

Add a table. Don’t rebuild the workshop.

A new stage makes three promises. That is the small “contract” every stage follows.

IN

What do I need?

“Give me the checklist and the evidence index.” Name the exact inputs, not “everything in the room.”

JOB

What do I do?

“Check whether the required proof is present.” One clear responsibility, with an explicit success or failure result.

OUT

What do I leave?

“A coverage note for the assessor.” Only helpers that need this new result must change.

The button above illustrates this addition. It does not run an AI model or change the real pipeline. A new report section may still need a renderer update.

04 / Rules that keep the test honest

No peeking. No guessing. No moving the goalposts.

Give each helper only its inputs

Putting “don’t peek” on a folder is not enough. Build separate model contexts and input payloads. Do not give the observer the entire run directory or our planning conversation.

But don’t promise perfect blindness

A recording may show a builder reading its instructions. Keep that real evidence and disclose the exposure. The observer may still infer what changed.

A missing photo is not a failed tower

If proof is missing, say “unknown.” If a job crashes, block jobs that require its output. Independent jobs may still continue.

One report, with visible corrections

The report is not automatically right. If the host finds an error, show the evidence and record a correction. Don’t quietly tell a different story in chat.

Review / Protect the folders

Same cabinet. Different envelopes.

Send only what is permitted

Keep the full recordings in the local cabinet. Each model gets a filtered, size-limited envelope with links back to its sources. Pick the observer’s pages without looking at the goal sheet; the assessor may prioritize goal-related pages. Sending more requires permission.

Put the observer in a separate room

A fresh empty working folder is only the start. Disable extra file access and automatic instruction loading too. If a host cannot enforce the boundary, show observation as unavailable rather than quietly letting it peek.

Still print what we know

A failed builder or helper must not hide the recordings. Print the available evidence and failure status even when no assessment is possible. Missing proof is not a negative verdict.

Corrections are attached notes

The host still checks the private test cases locally. Save attributed findings and corrections, show the latest account, and keep the original inspectable. Do not leak private notes into exported reports or send them to another provider. Old reports remain readable as old combined analyses, not invented fresh observations.

The refactoring plan defines the precise privacy, failure, status, correction, and historical-data contracts.

05 / One workshop, including development

Try your new tools
in the same workshop.

Developers can run the modified local Behavior Diff code. Normal use runs the installed version. Both follow the same headless trial path.

Two things must stay separate

The workshop tools: the Behavior Diff implementation being tested. Keep it fixed across both sides.

The builders’ instructions: the Before and After versions we are comparing. This is what differs between the sides.

Future direction: retire behavior-diff-live. It has not been removed by this page, and old reports do not need to disappear.

The grown-up version, in one minute
  • Keep: Bash/Python execution, fresh headless trials, agent-designed scenarios, frozen goals, original evidence, and deterministic rendering.
  • Separate: observation from goal assessment, using distinct model contexts and explicit inputs—not merely prompt wording.
  • Extend: an in-code registry names stages, input/output contracts, and dependencies. No general workflow framework is required.
  • Validate: check artifact structure and references. Valid JSON cannot prove a model’s interpretation is correct.
  • Record: stage completion, failure, skipping, and blocking separately from whether a tested goal was met.
  • Cost: a separate observer and assessor adds a model stage compared with today’s single extraction call. Better speed or accuracy must be measured, not assumed.
  • Not included automatically: new retries or provider fallbacks, caching, a plugin marketplace, or a user-facing workflow language. Preserve the existing Codex-to-Claude fallback only when it meets the same isolation rules and records the actual host/model.

The whole idea: each helper has one job, reads only the folders it needs, and leaves a result others can inspect. Add helpers by connecting their inputs—not by teaching every helper a whole new workflow.
